What Praxis can do today

Praxis is currently a Terraform module authoring and testing workspace. It turns public or uploaded modules into organization-owned wrappers, keeps those wrappers versioned, and tests saved revisions without cloud credentials.

Terraform Module Builder enabled AWS and Google Cloud modules OpenTofu 1.12 test runner Kubernetes development deployment
Current deployment configuration

The persisted .env enables terraform_module_builder. Modules & Stacks and the older Praxis tools exist in the repository, but they are not loaded into the current local UI.

Core model

Module layering

Git is the storage and versioning mechanism for Praxis modules. Each wrapper layer is created only from an immutable Praxis-managed release.

Upstream module terraform-aws-modules/vpc/aws
→
Praxis root module pds_network defines the stable company interface.
→
Praxis-managed Git release/tag v1.0.0 pins the released root-module commit.
→
Deployment wrapper pds_network_wrapper calls the released Praxis root module.
→
Praxis-managed Git release/tag A second immutable release makes the wrapper selectable.
→
Stack Selects an exact released deployment wrapper.
  1. pds_network wraps the public VPC implementation module.
  2. It defines organization inputs, outputs, defaults, validations, provider requirements, and naming conventions.
  3. After testing, Praxis commits the root module and creates an immutable semantic-version Git tag.
  4. pds_network_wrapper calls that exact Git-tagged root-module release.
  5. After its own test and release, the deployment wrapper becomes selectable by a Stack.
  6. Deployment code uses the organization layer instead of calling the public module directly.
module "pds_network" {
  source = "git::https://github.com/pollardbanknotelimited/pds_network.git?ref=v1.0.0"
}

Access and persistence

Authentication and workspace

Access

  • Local username and password authentication.
  • Optional Microsoft Entra ID authentication when configured.
  • Filesystem-backed authenticated sessions.
  • Global CSRF protection for state-changing forms.

Workspace behavior

  • Drafts belong to the signed-in user.
  • Drafts persist in SQLite on the Kubernetes persistent volume.
  • Light and dark themes are available.
  • The navigation displays the current runtime environment.

Discover

Finding Terraform modules

The Module Builder can search the public Terraform Registry, filter results between AWS and Google Cloud, and accept pasted Registry module addresses or URLs.

  • Browse available module versions and load an exact release.
  • Inspect the selected release's inputs, outputs, provider dependencies, and examples.
  • Open the module's Registry documentation.
  • Pin generated code to an exact version.

Registry browsing and imports need public internet access. Saved drafts and ZIP exports remain usable offline.

Author

Creating a regular module wrapper

For each upstream input, Praxis offers three choices:

Expose

Create a variable in the wrapper and forward it to the upstream module.

Fix a value

Embed a JSON string, number, boolean, list, or object directly in the module call.

Retain default

Omit an optional argument so the upstream module keeps its own default.

Select outputs

Expose selected upstream outputs. Generated outputs are conservatively marked sensitive.

Required upstream inputs must be exposed or assigned a fixed value. The generated draft normally includes main.tf, variables.tf, outputs.tf, versions.tf, and README.md.

Generated code carries the exact source and version, provider sources and constraints, supported aliases, input metadata, selected outputs, and source provenance.

Adapt

Starting from an upstream example

Instead of generating a thin wrapper, Praxis can copy an example from a GitHub-hosted module release into an editable draft.

  • Downloads the archive for the selected release.
  • Copies the selected example and its local nested modules.
  • Rewrites references to the repository root into the selected pinned Registry module.
  • Preserves relevant text assets and license notices.
  • Skips symbolic links and binary content and records review warnings.

This path is useful when an example includes additional resources, locals, provider configuration, or richer usage than a thin wrapper.

Import

Uploading an existing module

A Terraform module ZIP can be imported as an owned, editable draft. Uploading does not execute the archive.

  • Removes one common containing directory from repository ZIPs.
  • Preserves nested modules and UTF-8 text assets.
  • Requires Terraform files at the module root.
  • Rejects unsafe paths, links, encrypted ZIPs, binary content, and invalid Terraform syntax.
  • Excludes Git metadata, GitHub workflows, local state, plans, environment files, and variable-value files.
  • Limits uploads to 2.5 MB compressed, 2 MB text, and 200 imported files.

Maintain

Managing saved drafts

The Saved Drafts workspace shows the provider, name, draft type, revision, and available actions.

  • Edit any saved text file.
  • Add and remove files.
  • Rename a draft without rewriting its Terraform code.
  • Review import and generation warnings.
  • Inspect source provenance and detected module dependencies.
  • Download the saved module as a ZIP.
  • Delete a draft after revision-aware confirmation.

Every save creates a new revision. Optimistic revision checks prevent an older browser tab from silently overwriting newer changes.

Exports include the module files, praxis-source.json, and PRAXIS-IMPORT-NOTES.txt.

Layer

Creating deployment wrappers

Praxis can create a deployment wrapper only after the Praxis root module has a released Git commit and semantic tag. Releasing now requires a passing mock plan for the exact saved root revision. The newest release is selected by default, and any earlier released version remains selectable.

The inspection discovers:

  • Input variables, including type, default, description, and HCL validation blocks.
  • Outputs and sensitivity settings.
  • Provider configuration and required provider aliases.
  • Terraform requirements.
  • Existing root-level child module calls.

The screen shows the parent module, selected release, Praxis-managed source status, Git tag, and upstream provenance as read-only information. It does not ask for a Registry or Spacelift source.

The deployment wrapper passes all inputs through, forwards every output, preserves provider and Terraform declarations, and records the parent release, repository URL, tag, commit, draft, revision, and upstream provenance. It does not replace the Praxis root module with that module's internal public dependency.

Upgrade

Updating dependency versions

Public upstream dependencies and Praxis-managed parent releases follow separate update paths.

  • Update the public implementation version inside an organization module.
  • Select a newer immutable Praxis root-module release for its deployment wrapper.
  • Change only the selected module block.
  • Save the change as a new draft revision.
  • Update deployment-wrapper provenance when applicable.
  • Move directly to the test section after saving; wrapper release updates start a new mock test automatically.

Public upstream versions use exact semantic versions. Deployment wrappers use only Praxis release records whose semantic Git tag, commit SHA, repository URL, release version, and source snapshot agree. Results from the previous version remain attached to their older draft revision.

Verify

Formatting and OpenTofu validation

Each saved revision offers four actions:

ActionBehavior
Check formatting & validateChecks formatting, initializes dependencies without a backend, and runs configuration validation. This result alone cannot authorize a release.
Format filesFormats the saved files and stores changed output as a new draft revision.
Generate mock setupBuilds editable starting inputs, data-source defaults, and output expectations.
Run mock testRuns a plan-only OpenTofu test with mocked root providers. A passing result for the exact revision is required before release.

The results page reports the run state, tested revision, OpenTofu version, commands, durations, warnings, errors, generated test source, and whether the result is stale relative to the current draft.

Test without cloud credentials

Automatic mock generation and testing

Generating a starting setup

Praxis inspects module declarations and bundled examples to populate three editable JSON objects: input values, mock data defaults, and expected outputs.

  • Prefers literal inputs from an included example that calls the module root.
  • Finds required variables without defaults.
  • Infers sample values from variable types and names.
  • Creates sample regions, CIDRs, subnet/VPC/transit-gateway IDs, availability zones, names, booleans, lists, maps, and objects.
  • Finds referenced provider data sources and creates defaults for the attributes used by the module.
  • Turns literal outputs into starting assertions.

Running the test

The mock runner creates an OpenTofu plan test with mocked root providers. Root-module tests plan the selected third-party dependency and own compatibility checks after an upstream version update. Deployment-wrapper tests override the already-released parent module and verify wrapper wiring without planning the parent's internals again. Empty expected outputs produce a planning smoke test; supplied expectations are evaluated as assertions.

A wrapper bound to a tag created under the earlier validation-only rule cannot be mock-tested or released until the recorded parent revision has a passing root mock result.

These tests can reveal broken expressions, missing required values, invalid provider aliases, bad output references, and dependency compatibility problems. Generated samples must still be reviewed because Praxis cannot infer every organization-specific value.

Execution model

Isolated Kubernetes test runner

Every check creates a separate Kubernetes Job in the praxis-runs namespace.

Isolation

  • Read-only snapshot of one saved revision.
  • No application database or persistent-volume access.
  • No Kubernetes API token or Docker socket.
  • No AWS or Google Cloud credentials.
  • Non-root user, dropped capabilities, and read-only root filesystem.

Lifecycle

  • Disposable in-memory scratch storage.
  • CPU, memory, storage, and ten-minute limits.
  • No automatic retry after failure.
  • Result is saved before Job cleanup.
  • Cleanup resumes after a web Pod restart.

Dependency initialization can use public HTTPS. A private Praxis-managed GitHub release receives the signed-in user's saved GitHub credential through the one-run payload. Git can use it only for github.com during initialization; the temporary helper and token file are removed before validation or mock execution, when internet sockets are blocked. Other private Registry dependencies still require separate authentication.

Local operations

Development startup

The complete Rancher Desktop environment starts with:

./scripts/dev-start

The script builds the web and runner images, creates application and runner namespaces, prepares local authentication, creates or reuses persistent storage, applies ingress/RBAC/resource/network policies, maintains a local runner-image cache, waits for rollout, and preserves saved drafts across rebuilds.

Operational boundaries

What the active application does not do

  • It does not deploy infrastructure or run tofu apply.
  • It does not manage Terraform state.
  • It does not create cloud accounts, networks, buckets, clusters, or IAM roles.
  • It does not publish modules to a Registry.
  • It cannot automatically know every correct business value for generated mocks.
  • A passing mock does not prove real provider or cloud compatibility.
  • The test runner does not currently receive private Registry credentials.
  • GitHub pull-request submission is unavailable while Modules & Stacks is disabled.

Feature flags

Capabilities present in code but disabled

Modules & Stacks can be enabled alongside the builder with:

ENABLED_MODULES=terraform_module_builder,terraform_stacks

When enabled, it adds:

  • A shared module catalog and Git repository metadata.
  • Customers, environments, customer-specific accounts, and shared accounts.
  • Version-pinned stack definitions and stack YAML export.
  • Git tag, release, commit, and CI-check synchronization.
  • Generated module documentation from pinned releases.
  • Per-user GitHub App or fine-grained token settings.
  • Submission of passing Builder revisions through pull requests.
  • Optional explicit creation of private module repositories.
  • Release Please setup and patch/minor/major release selection.
  • GitHub Actions configuration validation.
  • Plan dispatch, approval tied to a commit and plan checksum, and apply dispatch.

Cloud execution remains off by default and requires deliberate GitHub, AWS OIDC, state-backend, role, and protected-environment configuration.
